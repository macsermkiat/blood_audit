Independent review of privacy, request identity, pilot transports, reporting, typing cleanup, and CI on 2026-10-19. The review excluded recovery, dashboard, and user-owned changes. This report describes the reviewed snapshot before subsequent fixes by the coordinator.

1. [CRITICAL] The verifier holds the signing secret. `src/bba/deid_redactor/admission.py:173` loads the HMAC signing key into the request-producing process. `verify` authenticates with that same key at line 185. This contradicts the issuer isolation contract in the module and `RedactionAuthority` documentation. A synthetic probe changed the user prompt to `Patient Alice Example HN 1234567`, recomputed the prompt digest, signed it with `policy._verification_key`, and passed `policy.verify`. No redactor ran for that changed prompt. Use an asymmetric issuer signature and give the application only its approved public key. Add a regression that proves the verifier cannot issue a valid approval.

2. [HIGH] Normal mixed pilot runs still fail reporting. `src/bba/report_generator/builder.py:287` requires uniform redactor version and model SHA. The pilot writes deterministic contexts with `not-applied` and `unavailable`, then replaces admitted LLM contexts with the actual redactor at `scripts/pilot/run_llm_leg.py:2825`. A synthetic two-row report raised `MixedRunMetadataError` for exactly that combination. Retain real row provenance and allow the explicit deterministic no-redaction sentinel while continuing to reject conflicting actual approved redactor identities. The mixed-model regression currently gives all rows the same redactor and misses this integration case.

3. [HIGH] New request manifests expose clinical evidence under the default umask. `src/bba/llm_client/request_identity.py:67,101` creates directories and files with default permissions. `scripts/pilot/_claude_cli_transport.py:208,209,345` does the same for manifests and responses. An executed probe under umask 022 produced a 0755 manifest directory and a 0644 manifest file. These files contain full clinical prompts and answers. Use owner-only directories and files, reject unsafe preexisting storage or validate it before use, and avoid following attacker-writable symlinks. Check permissions for both fresh and existing paths.

4. [HIGH] Pilot transport retries can silently repeat uncertain remote work. `src/bba/llm_client/transport.py:438,445` prepares a new random submission on every call. If the provider accepts a batch but the response is lost, the exception leaves no bound batch ID, and a repeated pilot command creates another submission. `RequestManifestStore.prepare` never checks an earlier unbound manifest for the same request. The recovery worker's pipeline-level uncertainty guard helps its own caller but the pilot directly invokes this transport. In the CLI path, `scripts/pilot/_claude_cli_transport.py:318` calls the remote runner before any per-request in-progress marker exists. A kill after provider execution but before the result rename makes resume rerun the model. Persist submission/attempt intent under a stable request identity, reject unresolved attempts as uncertain, and require reconciliation before resubmission. Add a fake provider that records acceptance and then raises, plus an interrupted CLI attempt test. The scenario follows the inspected call sequence; it was not executed against a live provider.

5. [MEDIUM] Manifest and CLI cache durability does not cover directory entries. `RequestManifestStore._write` fsyncs the file but not the containing directory at `src/bba/llm_client/request_identity.py:106`. The CLI manifest and successful result writes at `scripts/pilot/_claude_cli_transport.py:209,345` do not fsync their contents or the containing directory. A host crash can therefore lose the manifest or a completed cached answer after the operation returned. Use an owner-only temporary file, flush and fsync its contents, atomically install it, and fsync the parent directory. Ensure creation of the storage directory is durable when required. This is a durability gap inferred from filesystem semantics, separate from ordinary process interruption.
