Fix these boundaries before investing in visual redesign.

The improvement order should follow the risk and dependencies. First close R1 and add regression checks for R2 through R5. Treat crash recovery as a semantic-equivalence contract, including original request provenance. This phase is complete only when interrupted and uninterrupted runs produce equivalent decisions and retain the same evidence history.

Next establish the supported end-to-end composition in R7 and repair R6 and R10 within it. Make run, batch, audit, code version, request, and attempt identity explicit at each handoff. Then complete escalation and adjudication in R8 and R9. A reviewer must find an unresolved case, inspect its evidence, record a decision, and retrieve that decision after reload. Finish R11 alongside these changes so each repaired boundary becomes a required release check. This sequence gives maintainers one tested path to own.

Deployment hardening follows those repairs. Static inspection found that [dashboard snapshots read without a code-version selector](/Users/admin/Project_Chatbot_research/blood_audit/src/bba/dashboard/app.py:200). Multiple stored versions may therefore double-count cases. This was not reproduced at runtime. The dashboard also loads external Tailwind and HTMX scripts. Prefer compiled, locally served, versioned assets and verify deployment headers and caching. No CDN disclosure was demonstrated. Comment cleanup and minor typing debt belong after the correctness work.
