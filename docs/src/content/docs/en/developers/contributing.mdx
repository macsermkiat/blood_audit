Read the affected module's exports, callers, tests, and current documentation before editing. Keep the change focused and preserve unrelated work in the checkout.

## Create a branch

Use a descriptive branch under `feat/`, `fix/`, `refactor/`, `docs/`, `chore/`, `perf/`, `test/`, or `ci/`. For parallel work, create a separate worktree:

```bash
git worktree add ../blood_audit-topic -b docs/topic main
```

A worktree isolates files and branch state. `git worktree prune` removes stale metadata, not a working directory that you still need.

## Verify the change

Write a failing test for a behavior change, then implement the smallest fix. Test the business reason for the behavior, including the boundaries that would change an audit outcome. Use synthetic fixtures for clinical context.

Run the blocking checks in [Testing](/blood_audit/en/developers/testing/). Include database integration for changes to batch checkpoints or review actions. Report skips and unavailable validation explicitly. For documentation changes, build the site and inspect the affected pages and links.

Update current public contracts in `docs/CONTEXT.md` and the relevant operator, developer, or clinical pages. Keep dated implementation history separate from current instructions.

## Commit and review

Use a conventional commit message such as `fix: reject changed recovery evidence` or `docs: correct model admission setup`. Keep commits focused. Follow repository branch protection and review requirements when opening a pull request.

The repository convention uses merge commits through `gh pr merge --merge`. Confirm the required checks and independent review before merging. A green build does not establish clinical validation or deployment readiness.

`scripts/ralph_ticket.sh` supports the repository's ticket workflow. It generates test-first implementation and review steps. Use it when working through that workflow. It is not a prerequisite for understanding or testing a module.
